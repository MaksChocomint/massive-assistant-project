Запрос

POST /api/dialogues
{"text": "поставь будильник"}

201 — создание · 400 — бизнес-ошибка
404 — нет объекта · 409 — конфликт · 422 — валидация

Ответ 201 · фрагмент

{
  "intent": "alarm_set",
  "phase": "clarifying",
  "question": "На какое время поставить будильник?",
  "execution_confirmed": false
}

clarifying → awaiting_confirmation → ready → executed / execution_failed

Обязательные параметры → проверка формата → согласие → квитанция исполнения.

/answer продолжает диалог, /execution принимает результат. Квитанция: блокировка строки и идемпотентный повтор. Весь диалог — несколько транзакций. CRUD справочников, фильтры и единый формат ошибок сохранены.

9 связанных сущностей

45 атрибутов · 9 внешних ключей · связи 1:N и M:N

M:N: intent_slots и command_slots. Целостность: PK, FK, UNIQUE, CHECK и индексы. Схема: обратимые Alembic-миграции; bootstrap и seed для запуска.

Диаграмма построена из ORM-моделей: app/models/*.py и scripts/render_erd.py. Квитанция хранится в dialogue_sessions; commands.status=completed означает собранные параметры.

08 / Демонстрация

Три сценария с результатом в браузере

{
  "phase": "executed",
  "execution_confirmed": true,
  "execution_message": "Свет выключен."
}

После согласия адаптер выполняет действие и отправляет POST /api/dialogues/{id}/execution. История и аналитика читают сохранённый результат из БД.

Скриншоты работающего приложения. Для будильника подтверждается установка; для сигнала вкладка должна оставаться открытой. Физические лампы и системный будильник не подключены.

09 / Границы и развитие

Промежуточный ассистивный сервис

Ограничения текущей версии

  • 60 известных намерений; возможны ошибки на новых формулировках.
  • Слоты и даты ограничены словарями и правилами.
  • Исполнители работают в браузере; физические устройства не подключены.
  • Выбранный профиль, без идентификации голоса. Нет пользовательской авторизации и испытаний с незрячими участниками.

Подходы в реальных системах

Шаблоны и intent
Home Assistant: команды, параметры и реальные сущности дома.
Transformer-NLU
Предобученные модели для намерений и извлечения сущностей, например в Rasa.
LLM + инструменты
Модель формирует вызов; приложение проверяет и исполняет его.
Для реальной интеграции

Авторизованный адаптер → API устройства → проверенный результат → квитанция.

Нормализация времени · права доступа · таймауты · защита от повторного действия

Более сложная модель не заменяет согласование и проверку исполнения.

Примеры подходов: Home Assistant: voice architecture · Rasa: NLU components. Это варианты развития, не реализованные интеграции проекта.
