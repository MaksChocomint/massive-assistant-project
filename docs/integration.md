# Интеграция сервиса голосового диалога

Целевая система: голосовой помощник, умная колонка, доступное мобильное приложение
или контроллер умного дома. Клиент выполняет ASR/TTS, сервис уточняет текстовую
команду, внешний адаптер действительно вызывает устройство или сервис.

## Минимальный цикл

1. POST /api/dialogues с JSON {"text":"поставь будильник"}.
2. Озвучить spoken_text из ответа. Сохранить id диалога.
3. POST /api/dialogues/{id}/answer с {"answer":"на семь утра"}.
4. Озвучить полное действие и вопрос «Всё верно?». Отправить ответ пользователя
   тем же маршрутом: {"answer":"да"}. «Нет» завершает диалог отменой.
5. При phase=ready адаптер читает intent и slots и выполняет действие.
6. После проверки реального результата адаптер отправляет квитанцию:
   POST /api/dialogues/{id}/execution.
7. Клиент получает обновление GET /api/dialogues/{id} и озвучивает spoken_text.
   Веб-клиент опрашивает состояние раз в 3 секунды до 3 минут. После этого сообщает,
   что подтверждения нет; «Повторить вслух» снова проверяет сервер.

Пример тестовой квитанции, которая НЕ создаёт будильник:

    {"operation_id":"demo-alarm-001","success":true,
     "message":"Тестовая квитанция: обработчик подтвердил команду, устройство не подключено."}

Реальный адаптер должен посылать success=true лишь после подтверждения целевой системы.
Об ошибке сообщает success=false с понятным пользователю message. В проекте есть
браузерные адаптеры будильника, фона и даты/времени: они выполняют действие в
открытой вкладке и отправляют квитанцию тем же маршрутом. Другие намерения
требуют собственного исполнителя. Очереди доставки и подключения физических
устройств нет. Подробности: [браузерные исполнители](browser-execution.md).
После «да» интерфейс коротко подтверждает согласование параметров. ready_for_execution=true означает готовность к передаче; execution_confirmed остаётся false до успешной квитанции.
Внешний исполнитель должен получить id от своего клиента и прочитать GET.

## Состояния

| phase                 | Значение                           | Следующий шаг                             |
| --------------------- | ---------------------------------- | ----------------------------------------- |
| clarifying            | не хватает обязательного параметра | ответить на вопрос или отменить           |
| awaiting_confirmation | параметры собраны                  | озвучить действие, получить да/нет        |
| ready                 | пользователь согласовал            | ждать проверенного результата исполнителя |
| executed              | получена успешная квитанция        | озвучить подтверждение                    |
| execution_failed      | получена квитанция ошибки          | озвучить причину                          |
| cancelled             | пользователь отменил               | новый диалог                              |
| failed                | исчерпан лимит шагов уточнения     | озвучить незавершение, новый диалог       |

ready_for_execution=true только в ready. execution_confirmed=true только в executed.
Квитанция до согласования даёт 409. Точный повтор принятой квитанции идемпотентен;
попытка заменить результат другой квитанцией даёт 409. В PostgreSQL строка диалога
блокируется на время записи результата.

Отмена разрешена до ready. После передачи нельзя гарантировать отмену внешнего
действия без поддержки целевой системы. Новый диалог не отменяет предыдущий.

## Ответ и границы

Ответ содержит id, user (id/username/name/created_at), phase, intent, intent_name, confidence, slots (slot/name/value),
question, spoken_text, ready_for_execution, execution_confirmed, operation_id и
execution_message. Пустой текст отклоняется с 422; ошибки бизнес-правил дают 400,
недопустимые переходы — 409, неизвестный id — 404. Ошибки имеют единый формат error.

Время хранится строкой (например «семь утра»). Перед выполнением адаптер обязан
нормализовать дату, время и часовой пояс и при неоднозначности продолжить собственный
диалог. Прототип не гарантирует универсальную корректность понимания или слотов.
Для подключения к реальным устройствам нужны также аутентификация исполнителя,
права доступа, дедупликация самого внешнего действия и обработка отказов доставки.

Голос, текст и кнопки примеров записываются в один профиль. Это выбранный профиль,
а не биометрическое распознавание говорящего. Его данные возвращаются в user ответа

является подтверждением внешнего исполнения. Интеграция должна использовать /api/dialogues.
