Основная техническая часть соответствует итоговому заданию. Наличие работающего диалога и зелёных локальных тестов не закрывает эти пункты автоматически.

## Существенные замечания

### 1. В клиентском интерфейсе отсутствует часть обязательного минимума

Раздел 10 итогового задания требует просмотра списка объектов, создания, редактирования, ключевой бизнес-операции и отображения ошибок. В [основном экране](../app/static/index.html) есть создание диалога, уточнение, подтверждение, отмена и ошибки. Списка объектов и форм редактирования справочника нет. Протокол реплик одного диалога не заменяет список объектов. Swagger является документацией API и не даёт бесспорного выполнения отдельного требования к клиенту.

CRUD намерений уже реализован в [API](../app/api/catalog.py) и проверен test_intent_crud. Чтобы закрыть пункт и сохранить простой голосовой экран, достаточно отдельной страницы управления намерениями со списком, созданием, редактированием и отображением ошибок. Возвращать выбор пользователей в голосовой сценарий для этого не требуется. Это рекомендация; в ходе сверки интерфейс не изменялся.

### 2. Требования к GitHub и взаимному ревью не подтверждены

В локальной истории 27 коммитов; текущая ветка feat/final-project-ready. Однако git remote -v не выводит ни одного remote, а существенные текущие изменения и новые файлы ещё не закоммичены. Поэтому клонирование текущего состояния из GitHub и наличие настроек защиты main подтвердить нельзя. Это не утверждение об отсутствии других репозиториев пользователя.

Итоговое задание требует минимум 3 PR с описаниями, ревью минимум 2 PR коллеги и получение ревью минимум на 2 своих PR. На каждый проверяемый PR нужны минимум 3 содержательных замечания, ответы автора, итоговое Approve и зелёный CI перед слиянием. В отчёте должны быть ссылки. Шаблон PR и текст README эти факты не заменяют.

### 3. Аналитическое success_rate требует уточнения смысла

[Аналитика](../app/services/analytics.py) считает успех по commands.status=completed. После добавления голосового фасада этот статус означает собранные параметры, тогда как фактическая фаза хранится в dialogue_sessions. В проверочной рабочей БД есть диалоги ready и cancelled с commands.status=completed: например, отмена после проговаривания не отменяет факт сбора полей.

Таким образом, текущий success_rate нельзя представлять как долю реально исполненных действий. README объясняет старую семантику, но название поля и комментарий «успешно выполненных» в сервисе способны вводить в заблуждение. Нужно либо явно назвать метрику долей команд с собранными параметрами, либо добавить отдельную метрику по phase=executed. Четыре агрегации удовлетворяют количественному требованию раздела 7; замечание касается предметной интерпретации.

## Если требуется буквальное соответствие прошлым лабораторным

Эти расхождения относятся к отдельным работам и не являются автоматически дополнительными обязательными пунктами итогового ТЗ.

| Материал | Что совпадает | Что в текущем проекте не реализовано буквально |
| --- | --- | --- |
| Gist TASK2.md, каркас проекта | Настройки, логирование, ruff, pytest, покрытие, workflow, документация | Нет src-layout и устанавливаемого пакета, uv.lock, mypy, pre-commit, Typer-команды rg version/check-config, требуемых RG_* полей настроек, тега lab1 и docs/lab1_report.md |
| Практическая №2 | FastAPI, PostgreSQL, ORM Mapped, Pydantic, Depends, Alembic | Синхронные сессии вместо AsyncSession; другая предметная область и маршруты; нет middleware X-Process-Time и полного лога метод/путь/статус/время. Нет комплекта скриншотов Swagger/psql и ответов на её контрольные вопросы |
| Практическая №3 | Тестов больше 9, Docker/Compose, непривилегированный пользователь, healthcheck, миграции до запуска, lint/test в workflow | pytest работает на SQLite, а работа требует реальную PostgreSQL; Dockerfile одностадийный; нет публикации образов в GHCR/Docker Hub; не подтверждены намеренно красный PR и его исправление, ссылки/скриншоты pipeline, ответы на контрольные вопросы и команда тестов через Compose |
| Лабораторная №10, ипотечный ML-сервис | Есть текстовая предобработка, train/dev/test, ML, FastAPI и клиент | Нет ипотечной задачи, сравнения двух обучаемых алгоритмов по ROC-AUC, сохранённой модели pkl и загрузки, /upload-model, /predict, /predict-from-csv, Sourcecraft CI и описанного командного процесса |

Для MASSIVE многоклассовая accuracy/macro F1 имеет другой смысл, чем ROC-AUC ипотечной задачи. Требование реализовать ипотечные endpoint'ы нельзя переносить в голосовой сервис без изменения темы. Сначала нужно определить, должны ли лабораторные сдаваться отдельно или преподаватель требует перенести отдельные приёмы в итоговый проект.

- Живой OpenAPI: 26 API-операций; фильтрация/сортировка/пагинация намерений и четыре агрегирующих маршрута ответили 200.
- Неизвестный объект и неизвестный маршрут: 404 в едином формате; некорректная сортировка: 422 в том же формате.
- PostgreSQL: 9 таблиц приложения, 15 642 фразы, текущая ревизия b962ae7d1f40.
- Проверена взаимосвязь dialogue_sessions.phase и commands.status; подтверждено замечание к смыслу success_rate.
- Контейнеры app и db healthy. Рабочая база не откатывалась и не очищалась.

## Порядок доведения до сдачи

1. Закрыть §10 отдельной страницей управления справочником, сохранив простой голосовой экран.
2. Уточнить смысл аналитического успеха относительно нового цикла исполнения.
3. Зафиксировать текущие изменения, связать клон с реальным репозиторием, настроить защиту main и провести требуемые PR/review с одногруппниками.
4. Получить зелёный GitHub CI на сдаваемом состоянии и добавить ссылки на CI/PR/review в README или отчёт.
5. Подтвердить согласование темы и подготовить демонстрацию на 7–10 минут. Сквозное управление реальным устройством не заявлять: проект реализует микросервис уточнения и контракт исполнителя, а не готовый умный дом.

Во время сверки исходный код приложения не изменялся. Создан этот отчёт и обновлены локальные отчёты покрытия.
