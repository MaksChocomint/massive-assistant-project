# MASSIVE. Диалог — ассистивный сервис голосовых команд

[![CI](https://github.com/MaksChocomint/massive-assistant-project/actions/workflows/ci.yml/badge.svg)](https://github.com/MaksChocomint/massive-assistant-project/actions/workflows/ci.yml)

Итоговый проект по дисциплине «Разработка на Python и инженерия данных».
Информационная система на **FastAPI + PostgreSQL** на основе открытого датасета
[MASSIVE](https://github.com/alexa/massive) (русская часть, 16 521 фраза).

## Предметная область

Ассистивный голосовой интерфейс для незрячего пользователя. Сервис предназначен
для встраивания между распознаванием речи и исполнителем: голосовым помощником,
планировщиком будильников, контроллером умного дома или сервисом календаря.
При работе без зрения система должна задать недостающие вопросы, зачитать параметры,
получить согласие и озвучить проверенный результат.

«Поставь будильник» → «На какое время?» → «На семь утра» → проговаривание команды
и «Всё верно?» → «Да» → ожидание ответа исполнителя. Только отдельная квитанция
исполнителя позволяет сообщить об успехе. При отсутствии квитанции действие не
объявляется выполненным.

В демо доступны голосовой ввод и синтез речи. Firefox записывает короткую фразу через
Web Audio, FastAPI распознаёт её локальной русской моделью Vosk и передаёт текст
в диалог на основе MASSIVE. В Chrome/Edge при наличии используется распознавание
самого браузера. Вкладка также работает исполнителем трёх сценариев: будильник
со звуковым сигналом, переключение светлого/тёмного фона и текущие дата и время.
Физические устройства умного дома не подключены.
Доступен текстовый ввод и экранный диктор. Подробнее: [голос в Firefox](docs/speech.md).

Контракт интеграции и состояния: [docs/integration.md](docs/integration.md).

В меню доступна **«История и аналитика»**: команды из БД, фильтры по пользователю,
периоду и результату, поиск, параметры и квитанции, частые намерения, активность
пользователей и динамика по дням. Выполненными считаются только команды с успешной
квитанцией. Подробнее: [docs/activity.md](docs/activity.md).

### Что попробовать

Скажите или введите команду, дождитесь проговаривания и подтвердите «да».
Кнопки справа подставляют те же фразы в обычный диалог, сохраняя этап подтверждения.

| Команда                                | Результат после «да»                                                           |
| -------------------------------------- | ------------------------------------------------------------------------------ |
| «Поставь будильник через минуту»       | Отсчёт справа, затем повторяющийся звуковой сигнал; кнопка «Остановить сигнал» |
| «Выключи свет» / «Включи свет»         | Фон страницы становится тёмным / светлым                                       |
| «Какой сегодня день и сколько времени» | Дата, день недели и время устройства, с озвучиванием                           |

После действия браузер отправляет настоящую квитанцию в API: `phase=executed`,
`execution_confirmed=true`, а `execution_message` содержит результат исполнителя.
У будильника подтверждается **установка**; сигнал прозвучит по истечении срока.
Оставьте вкладку открытой: это браузерный будильник, а не системный планировщик.
После перезагрузки нажмите «Включить звук будильника», если браузер его заблокировал.
Если действие не удалось, сервер сохраняет `execution_failed` и причину ошибки.
Подробности и ограничения: [браузерные исполнители](docs/browser-execution.md).

**Стек:** Python 3.12, FastAPI, SQLAlchemy 2, Alembic, PostgreSQL 16, Pydantic 2,
scikit-learn, React 19 + Vite, pytest, ruff, Prettier, Docker Compose, GitHub Actions.

Архитектурно это один самостоятельно запускаемый FastAPI-сервис с собственной БД и модульной структурой. Его можно встроить в микросервисную систему как компонент уточнения команд; распределённая микросервисная архитектура в самом проекте не реализована.

## Запуск

### Через Docker (рекомендуется)

```bash
cp .env.example .env
docker compose up -d --build --wait
```

PowerShell: вместо `cp` можно использовать `Copy-Item .env.example .env`.
Приложение само применяет миграции, импортирует CSV и создаёт учебные примеры команд.
Голосовой экран использует выбранный профиль **maksim ivanov** (`maksim_ivanov`).
Он создаётся автоматически; история прежнего `voice_dialogue` переносится к нему.
Профиль общий для голоса, текста и кнопок примеров; распознавания личности по голосу нет.
Повторный запуск сохраняет существующие данные. Первичная сборка скачивает зависимости;
для текстовой модели сеть не нужна. Голосовой ввод зависит от браузера и его сервиса.

- веб-интерфейс: <http://localhost:8000/>
- история и аналитика: <http://localhost:8000/history>
- Swagger: <http://localhost:8000/docs>
- презентация из 9 слайдов: <http://localhost:8000/presentation> (стрелки, печать в PDF).

Если порты заняты, измените `APP_PORT` и `DB_PORT` в `.env`, например на `8010` и `5435`.
Тогда интерфейс открывается на `http://localhost:8010`. Для локального Python также
измените порт в `DATABASE_URL`. Внутри Docker приложение использует адрес `db:5432`.

### Локально

```bash
python -m venv .venv && source .venv/bin/activate    # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
cp .env.example .env                                 # указать DATABASE_URL своей БД
docker compose up -d db                              # или свой PostgreSQL
python -m app.bootstrap
uvicorn app.main:app --reload
```

`python -m app.bootstrap --no-demo` применяет только миграции. Для диагностики Docker:
`docker compose ps` и `docker compose logs app`. Остановка: `docker compose stop`.

### Переменные окружения

| Переменная            | Назначение                              | По умолчанию                                            |
| --------------------- | --------------------------------------- | ------------------------------------------------------- |
| `DATABASE_URL`        | подключение к PostgreSQL                | `postgresql+psycopg://app:app@localhost:5432/assistant` |
| `MAX_CLARIFICATIONS`  | сколько раз можно уточнять одну команду | `3`                                                     |
| `LOG_LEVEL`           | уровень логирования                     | `INFO`                                                  |
| `DB_PORT`, `APP_PORT` | порты на хосте для `docker compose`     | `5432`, `8000`                                          |

## React-интерфейс

Исходники находятся в [frontend](frontend/README.md). Используется упрощённый FSD:
app → pages → widgets → features → shared. Голос и диалог выделены в независимые
features, а координация сценария находится в widgets/assistant/model.

При локальном запуске Python сначала соберите интерфейс:

```powershell
npm ci --prefix frontend
npm run build --prefix frontend
```

В Docker сборка выполняется автоматически. Для разработки с горячим обновлением:
npm run dev --prefix frontend; запросы к API проксируются на localhost:8010.

Проверки frontend: npm test --prefix frontend. Форматирование всех поддерживаемых
исходников: npm run format --prefix frontend; проверка: npm run format:check --prefix frontend.
Python проверяется ruff. CI запускает оба набора проверок и production-сборку React.

## База данных

9 таблиц, схема и ограничения — в [docs/erd.md](docs/erd.md).

| Таблица             | Что хранит                                                        |
| ------------------- | ----------------------------------------------------------------- |
| `scenarios`         | сценарии (будильник, погода, календарь…)                          |
| `intents`           | намерения, принадлежат сценарию (1:N)                             |
| `slot_types`        | типы параметров (время, дата, город…)                             |
| `intent_slots`      | **M:N** намерение ↔ параметр: обязательность, порядок, вопрос     |
| `utterances`        | фразы датасета с разметкой (1:N к намерению)                      |
| `users`             | пользователи                                                      |
| `commands`          | команды пользователей: намерение, уверенность, статус             |
| `command_slots`     | **M:N** команда ↔ параметр: найденное значение                    |
| `dialogue_sessions` | фаза согласования и квитанция исполнения, связь 1:0..1 с commands |

Ограничения: PK/FK, `NOT NULL`, `UNIQUE` (коды, `username`, `external_id`),
`CHECK` (статус, partition, неотрицательные счётчики), индексы на полях фильтрации.
Миграции Alembic обратимы: `alembic downgrade base` удаляет всё.

## Бизнес-правила

Реализованы в слое `app/services`, проверяются тестами:

1. **Команда без обязательного параметра не готова к передаче** — статус `needs_clarification`
   и вопрос по первому недостающему параметру (по порядку `position`).
2. **Ответ на уточнение проверяется по формату**: время и дата должны быть похожи на
   время и дату («напиши музыку» вместо времени → 400).
3. **Лимит уточнений**: считаются и успешные, и неудачные ответы. Если после исчерпания
   `MAX_CLARIFICATIONS` шагов остаются незаполненные параметры, команда переходит в `failed`.
4. **Уточнять и отменять можно только активную команду** — выполненную или отменённую нельзя (409).
5. **Нельзя удалить намерение, которое используется** — есть команды или фразы датасета (409).
6. **Уникальность**: код намерения и логин пользователя не повторяются (409).

## ETL

Источник, состав CSV и атрибуция датасета: [data/README.md](data/README.md).

```bash
python -m app.etl.import_massive --source data/massive_ru.csv
```

| Этап             | Что делается                                                                                                                                                                                                                        |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Extract          | чтение CSV, проверка обязательных колонок                                                                                                                                                                                           |
| Validate / Clean | пустые поля, неизвестный `partition`, неверные идентификаторы, повтор `id`, дубликаты фраз (без учёта регистра и пробелов), сломанная или несогласованная с текстом разметка `[slot : value]` — такие строки отклоняются с причиной |
| Transform        | нормализация текста, названия на русском, список параметров из разметки                                                                                                                                                             |
| Load             | сценарии, намерения, параметры, связи M:N и фразы; уже загруженные `external_id` пропускаются                                                                                                                                       |

Повторный запуск **идемпотентен** — дубли не появляются:

```
первый запуск:  прочитано 16521, загружено 15642, уже в БД 0, отклонено 879 (дубликат фразы: 879)
второй запуск:  прочитано 16521, загружено 0, уже в БД 15642, отклонено 879 (дубликат фразы: 879)
```

## API

Основной клиент использует фасад диалога без user_id:

| Метод | Путь                            | Назначение                                |
| ----- | ------------------------------- | ----------------------------------------- |
| POST  | `/api/dialogues`                | создать диалог, тело: text                |
| GET   | `/api/dialogues/{id}`           | состояние, вопрос и текст для озвучивания |
| POST  | `/api/dialogues/{id}/answer`    | ответ или согласие, тело: answer          |
| POST  | `/api/dialogues/{id}/cancel`    | отмена до передачи                        |
| POST  | `/api/dialogues/{id}/execution` | квитанция внешнего исполнителя            |

Параметры → проговаривание → «да» → ready → квитанция → executed/execution_failed.
ready означает согласованную команду, а не выполнение действия. Квитанция до
подтверждения отклоняется; её точный повтор идемпотентен. Подробности — в
[контракте](docs/integration.md). API физические действия не выполняет.

Учебные CRUD и агрегирующие маршруты сохранены ниже. Старый commands.status=completed
означает собранные параметры; он не подтверждает работу устройства.

Единый формат ошибок: `{"error": {"code": "...", "message": "...", "details": [...]}}`.
Коды: 200, 201, 204, 400 (бизнес-правило), 404, 409, 422 (валидация),
503 (нет достаточных данных для обучения).

| Метод  | Путь                             | Описание                                                                                                    |
| ------ | -------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| GET    | `/api/intents`                   | список: пагинация `limit/offset`, фильтры `scenario_id`, `active`, `search`, сортировка `sort=name` / `-id` |
| GET    | `/api/intents/{id}`              | намерение                                                                                                   |
| POST   | `/api/intents`                   | создать (201)                                                                                               |
| PATCH  | `/api/intents/{id}`              | изменить                                                                                                    |
| DELETE | `/api/intents/{id}`              | удалить (204, или 409 если используется)                                                                    |
| GET    | `/api/scenarios`                 | сценарии с числом намерений                                                                                 |
| GET    | `/api/slot-types`                | типы параметров                                                                                             |
| POST   | `/api/users`                     | создать пользователя                                                                                        |
| GET    | `/api/users`, `/api/users/{id}`  | пользователи                                                                                                |
| POST   | `/api/commands`                  | отправить команду (распознавание + бизнес-правила)                                                          |
| GET    | `/api/commands`                  | список: фильтры `status`, `user_id`, пагинация                                                              |
| GET    | `/api/commands/{id}`             | команда                                                                                                     |
| POST   | `/api/commands/{id}/clarify`     | ответ на уточняющий вопрос                                                                                  |
| POST   | `/api/commands/{id}/cancel`      | отменить команду                                                                                            |
| GET    | `/api/analytics/top-intents`     | топ-N намерений и доля успешных                                                                             |
| GET    | `/api/analytics/status-summary`  | команды по статусам                                                                                         |
| GET    | `/api/analytics/commands-by-day` | динамика команд по дням                                                                                     |
| GET    | `/api/analytics/dataset`         | фразы датасета по сценариям                                                                                 |
| POST   | `/api/nlu/train`                 | переобучить модель, точность на dev                                                                         |
| GET    | `/api/health`                    | проверка работы                                                                                             |

Примеры:

```bash
curl -X POST localhost:8000/api/commands -H "Content-Type: application/json" \
     -d '{"user_id": 1, "text": "поставь будильник"}'
curl -X POST localhost:8000/api/commands/1/clarify -H "Content-Type: application/json" \
     -d '{"answer": "на семь утра"}'
curl "localhost:8000/api/intents?scenario_id=1&sort=name&limit=5"
curl "localhost:8000/api/analytics/top-intents?limit=5"
```

## Веб-интерфейс

Страница `/` содержит практический диалог: «Говорить», вопрос помощника,
«Повторить вслух», отмену и текстовый резерв. Каталог, пользователи и аналитика
доступны через Swagger; выбирать аккаунт для команды не требуется.

Микрофон включается по нажатию «Говорить» или Alt+M. После озвучивания вопроса
клиент снова слушает. Alt+R повторяет ответ, Escape останавливает речь и микрофон,
сохраняя команду. Последний диалог восстанавливается после перезагрузки.
Автоматического доступа к микрофону при открытии страницы нет.

Поддерживаются актуальные Firefox и Chrome/Edge на localhost или HTTPS.
В Docker русская модель для Firefox устанавливается при сборке; локально выполните
`python -m app.speech.prepare`. При недоступности микрофона или сервиса появляется понятная
ошибка и текстовый ввод. Русский голос зависит от установленных голосов ОС.
При использовании экранного диктора собственное озвучивание можно отключить.
Скорость собственного озвучивания регулируется от 0,5× до 2× (шаг 0,1),
сохраняется в браузере и применяется к следующему прочтению. Ползунок доступен
с клавиатуры; кнопка «Повторить вслух» читает сообщение с выбранной скоростью.

## Тесты

```bash
pytest --cov-report=html     # 146 тестов; порог покрытия 70 %
ruff check . && ruff format --check .
```

Последний локальный прогон: **146 passed, покрытие 92,37 %** (Python 3.13).
Frontend: **16 тестов**, включая исполнение и повторную доставку квитанций.
HTML-отчёт создаётся в `htmlcov/index.html`, в CI сохраняется `coverage.xml`.

Тесты используют отдельную БД — SQLite в памяти (`tests/conftest.py`), данные — небольшая
выборка `tests/fixtures/sample.csv` (265 фраз, 8 намерений).

- `test_etl.py` — unit: очистка, причины отклонения, идемпотентность;
- `test_services.py` — unit: бизнес-правила;
- `test_models.py` — ограничения UNIQUE / CHECK / FK;
- `test_api.py` — интеграционные через TestClient, включая негативные сценарии.
- `test_seed.py`, `test_evaluate.py` — идемпотентность демо-данных и оценка модели.
- `test_dialogue.py` — согласование, состояния, ошибки и идемпотентная квитанция.

## Оценка качества модели

```bash
docker compose exec app python -m app.evaluate --output /tmp/evaluation.json
docker compose cp app:/tmp/evaluation.json docs/evaluation.json
# Локально: python -m app.evaluate --output docs/evaluation.json
```

Отчёт содержит accuracy, macro F1, частотный baseline и самые частые ошибки отдельно
для dev и test. TF-IDF и SVM обучаются **только на train**, `random_state=42`.
Чистка удаляет повторы фраз, сохраняя первое вхождение в исходном CSV, поэтому
размеры разделов после импорта отличаются от исходных. Test не используется для
подбора параметров. [Зафиксированный результат](docs/evaluation.json).

Измерение на включённом CSV (60 активных намерений, 10 907 обучающих фраз):

| Выборка | Фраз после очистки | Accuracy | Macro F1 |
| ------- | ------------------ | -------- | -------- |
| dev     | 1 916              | 82,99 %  | 77,86 %  |
| test    | 2 819              | 82,80 %  | 78,59 %  |

Ограничения: классификатор выбирает одно из известных намерений; полноценного
обнаружения неизвестных тем нет. Параметры извлекаются словарём и регулярными
выражениями; это не универсальная языковая модель. Новое намерение без обучающих
примеров доступно в справочнике, но не становится распознаваемым автоматически.

Пошаговая работа с ветками и PR описана в [CONTRIBUTING.md](CONTRIBUTING.md).

Первичная публикация сохраняет историю разработки и текущий рабочий проект в main.
Дальнейшие изменения оформляются через PR. Сам факт настройки GitHub не заменяет
требуемое методичкой ревью: до сдачи нужны минимум 3 PR, ревью минимум двух своих
и двух чужих PR с содержательными замечаниями. Подробности — в
[сценарии защиты](docs/defense.md).

Результаты фактических локальных проверок: [docs/verification.md](docs/verification.md).
